## Bug fixed: `future_reads` was a dead-code tautology

Before this work, the future-read count feeding `GOLD_PROMOTION_PRECONDITIONS`'s
`no_future_read_violations` and `max_source_step_below_every_cutoff` entries was computed as
`future_reads = ... if False else 0` — an unconditional `0` regardless of the data, so both gate
entries always passed no matter what the build actually did.

Fixed by `probe_future_read_violations()` in `features/build_offline.py`: a second, independently
written self-join against the DuckDB source relation. It does not call
`paysim_pre_decision_feature_sql`, `_prior_window_predicate`, or `_derived_window_columns` from
`features/paysim_recipient.py` — calling the engine under test to audit the engine under test would
make the gate self-certifying.

Design detail that matters: the row-selection filter (which prior rows are "in range" for a cutoff)
is expressed on `step`, while the violation condition is expressed on `knowledge_step >=
cutoff_step`. Using the same column for both the filter and the violation condition would turn the
check into a tautology — a row that passed the step filter could never also fail a step-based
violation condition, so the gate would pass unconditionally by construction, exactly like the bug
it replaces. Keeping the two conditions on different columns (`step` for range membership,
`knowledge_step` for the violation itself) is what gives the check the ability to fail.

**Mutation test, run by hand:** changing the violation condition from `knowledge_step >=
cutoff_step` to `knowledge_step > cutoff_step` made
`tests/unit/test_gold_future_read_audit.py::test_probe_future_read_violations_catches_a_late_known_history_row`
go red (`assert 0 == 1`, since a row with `knowledge_step == cutoff_step` no longer counted as a
violation under `>`). Reverting to `>=` restored green. This is direct evidence the test has teeth,
not just that it passes.

## Limitation that must not be misread as "the gate is exercised end to end"

On the current ingested data, `knowledge_step = step` is assigned for every row at ingest time in
`data/paysim.py` (ADR-005 clean-data invariant). Consequently `probe_future_read_violations()`
**never returns nonzero on this data** — the gate cannot organically fire. What changed is not that
the gate now catches something; on this data it still returns 0 either way. What changed is that
the `0` is now **proven** by an independent self-join computation over the actual rows, rather than
**assumed** by a hard-coded literal that never looked at the data at all. The mutation test above is
what demonstrates the difference, since it shows the function can return nonzero under a
deliberately broken definition.

A second, related limitation: `probe_future_read_violations()` is a second independent derivation
next to `paysim_pre_decision_feature_sql`, so it cannot catch a boundary bug that exists only inside
`paysim_pre_decision_feature_sql` itself (e.g. an off-by-one in the frozen engine's own window
predicate) — it would need to reproduce that exact bug to agree with it, and it does not, by
construction.

## Other known gaps, not closed here

- `compare_gold_against_reference(scope="random_sample")` remains
  `raise NotImplementedError(...)` — guide §4.1 requires agreement on **both** the fixture and a
  random sample before benchmarking; only the fixture-scope path (`scope="fixture"`) has been
  exercised. The pure-Python oracle in `paysim_reference.py` is near-quadratic in the row count it
  scans, so running the fixture-scope comparison over a wide multi-step range would be expected to
  hang or take impractically long; this is a reason the random-sample path needs a different
  strategy, not just an implementation of the current one at larger scope.
- `export_feast_source_parquet()` is still `raise NotImplementedError("T2 round-0 skeleton")` — how
  Feast reads full-scale Gold (export Parquet / Feast DuckDB offline-store view / keep Feast at
  fixture scale) remains the open decision recorded in HANDOFF.md §6 item 1.

## Part A decisions finalized this session

Two previously-open decisions from HANDOFF.md §6 items 3 and 4 were finalized and
`docs/feature-store/sprint-2-implementation-guide.md` was corrected to match (§5.2 and §11), with
the change logged in the guide's own "Nhật ký hiệu chỉnh" section under 2026-08-04:

1. **Idempotency-key prefix is kept in code; the guide's literal 5-field formula was the
   out-of-date side.** The guide now states the key as
   `sha256(policy_version + "\0" + dataset_snapshot + "\0" + entity_version + "\0" +
   feature_version + "\0" + start + "\0" + end)`, current `policy_version` value
   `backfill-idempotency-key-v1`, separator `\0` rather than an implied `+`/`:` (`:` was rejected
   because `dataset_snapshot_id` already contains `:`, e.g. `paysim1:16910f90577b0d98`, so a `:`
   separator could let two different inputs collide on the same byte string).
2. **No `e2e` pytest marker is added.** `pyproject.toml` is one of `GOLD_COMPONENT_PATHS` and
   appears in both ADR-004 `component-fingerprint-v1` boundaries (lakehouse and training); adding a
   marker line would move both fingerprints and invalidate the exact-Silver reuse the project
   depends on. E2E selection stays on path (`pytest tests/e2e`) plus the existing `integration`
   marker. The guide's §11 (T9 test suite) previously said nothing about this; it now records the
   decision and the reason inline.

No `docs/adr/` file, test, or `src/` code outside `features/build_offline.py` (already modified
before this session) was touched to make these two decisions; only the guide was edited, per this
session's scope.
